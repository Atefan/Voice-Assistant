Talk_Project - build, test & debug
==================================

BUILD & RUN
-----------
First time only (downloads GoogleTest into build/_deps):

    cd ~/Talk_Project
    cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug

Every time after that:

    cmake --build build -j4
    ./build/talk_server

-DCMAKE_BUILD_TYPE=Debug is what gives -g -O0, so gdb shows real variable
values instead of <optimized out>. Always build Debug when debugging.

TESTS
-----
    ctest --test-dir build --output-on-failure

Or run the binary directly - more readable output:

    ./build/tst/test_tasks
    ./build/tst/test_tasks --gtest_filter='*Fifo*'
    ./build/tst/test_tasks --gtest_list_tests     # list names, run nothing
    ctest --test-dir build -R Fifo                # filter by name
    ctest --test-dir build --rerun-failed         # only what failed last time

Start over from scratch:

    rm -rf build
    cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug

VS CODE DEBUGGING
-----------------
Needs the C/C++ extension (ms-vscode.cpptools).

    F5              start debugging (uses .vscode/launch.json)
    F9              toggle breakpoint on the current line
    F10             step over
    F11             step into
    Shift+F11       step out
    Shift+F5        stop
    Ctrl+Shift+F5   restart
    Ctrl+Shift+B    build (the default build task)

Launch configs in the dropdown at the top of the Run and Debug panel:
    Debug talk_server               - breaks at the first line of main()
    Debug test_tasks                - the whole test binary
    Debug one test (prompts...)     - asks for a --gtest_filter
    Attach to a hung process        - pick the PID when something is stuck

Watch panel: click + and type an expression, e.g.  tasks.size()  or  stopped
Variables panel shows locals automatically; pretty-printing is on, so a
std::vector<char> shows its bytes rather than its internal pointers.
Call Stack panel has a thread dropdown - use it when a worker thread is stuck.
Debug Console accepts gdb commands if you prefix them with -exec, e.g.
    -exec thread apply all bt

GDB FROM THE TERMINAL
---------------------
    gdb ./build/talk_server
    (gdb) run
    (gdb) break Tasks.cpp:22       # break in dequeueTask
    (gdb) info threads
    (gdb) thread apply all bt      # every thread's stack - use this on a hang
    (gdb) print tasks.size()
    (gdb) continue

    gdb --args ./build/tst/test_tasks --gtest_filter='*Fifo*'

If a test or the server hangs, Ctrl-C it in gdb then run
"thread apply all bt". A frame inside __pthread_cond_wait means a dequeue
that nobody will ever wake - dequeueTask() blocks until a task arrives or
terminate() is called.

THREADSANITIZER
---------------
Catches data races even when nothing crashes. Use it for anything touching
TaskQueue from several threads - a passing threading test only means you got
lucky that run.

    cmake -S . -B build-tsan -DCMAKE_BUILD_TYPE=Debug \
        -DCMAKE_CXX_FLAGS="-fsanitize=thread -g"
    cmake --build build-tsan -j4
    ./build-tsan/tst/test_tasks

SOCKET SERVER
-------------
talk_server takes no command line arguments. Which path runs is decided by the
runDirect flag at the top of main() in src/Server.cpp:

    runDirect = true    one request straight through TaskHandler, no sockets
    runDirect = false   the socket server: listen, accept one client, serve it

Both paths construct a TaskHandler, so both load Qwen (llama) and whisper
first. Expect roughly a minute of model loading before anything happens.

    ./build/talk_server

With runDirect = false it prints "Server: listening on port 5555" once the
models are up, then blocks in accept() until a client connects.

ONE CLIENT PER RUN
------------------
connectToClient() closes the listening socket after accept() returns, so the
server handles exactly one connection and then exits. There is no reconnect -
restart the process for another client. The connection itself stays open
across any number of requests.

THE LAYERS
----------
    Sockets.cpp     bytes on an fd           knows nothing about Task
    Protocol.cpp    Frame <-> Task           knows nothing about fds or models
    TaskHandler     Task  -> answer string   knows nothing about the wire

Turning a Task into a prompt is jsonToChatML() in ChatML.h, called from
TaskHandler::handleText() - deliberately not in Protocol.cpp, or two files
would decide what a prompt looks like.

WIRE FORMAT (inc/Sockets.h)
---------------------------
    byte 0..3   uint32, network byte order   type
    byte 4..7   uint32, network byte order   length
    byte 8..    length bytes                 payload

Request type is a TASK_TYPE: 0 = TYPE_TEXT (UTF-8 JSON payload), 1 = TYPE_AUDIO
(raw little-endian 16-bit PCM). Replies use FRAME_TYPE_REPLY = 0xFFFFFFFF, not
0 - TYPE_TEXT is already 0, so a reply would be indistinguishable from a text
request. A reply payload is the JSON string TaskHandler::handle() returned.

Task::connectionID is the client fd, so main replies with
sendFrame(task.connectionID, ...). That only works because there is exactly one
connection: fd numbers are recycled, so with several clients a queued task
could carry a number that now belongs to someone else. Multi-client needs a
monotonic connection id instead.

THERE IS NO CLIENT YET
----------------------
Nothing in this project connects TO the server - only the server half is
written. To exercise it, save this as /tmp/talk_client.py:

    import socket, struct, json
    s = socket.create_connection(("127.0.0.1", 5555)); s.settimeout(600)
    req = {"messages": [{"role": "user", "content": "What is 2 plus 2?"}]}
    p = json.dumps(req).encode()
    s.sendall(struct.pack("!II", 0, len(p)) + p)          # 0 = TYPE_TEXT
    h = s.recv(8); t, n = struct.unpack("!II", h)
    body = b""
    while len(body) < n: body += s.recv(n - len(body))
    print(t, body)                                         # t = 4294967295
    s.close()

    python3 /tmp/talk_client.py

netcat is not much use here - the protocol is binary and length-prefixed, so
nc can only prove that accept() works, not that framing does.

ERRORS
------
Everything in the socket layer throws SocketError (inc/Errors.h) rather than
returning -1. A malformed request throws RequestError and the Listener answers
it with {"error": ...} and keeps the connection alive; a socket failure ends
the connection. main catches both and prints them - it never rethrows out of
main, because an uncaught exception there calls std::terminate and ggml's
handler buries the message under a backtrace.

SOCKET DEBUGGING
----------------
Is it actually listening, and on which address?

    ss -ltnp | grep 5555
    # LISTEN 0 4 0.0.0.0:5555   <- all interfaces; Send-Q 4 is LISTEN_BACKLOG
    # Recv-Q on a LISTEN row = connections waiting to be accepted

    ss -tnp | grep 5555          # established connections
    strace -f -e trace=network ./build/talk_server      # every syscall + errno
    sudo tcpdump -i lo -X port 5555                     # the bytes on the wire

"Address already in use" should not happen - SO_REUSEADDR is set before bind().
If it does, something else really is on the port: ss -ltnp will name it.

SIGPIPE kills the process on a write to a closed peer. sendAll() passes
MSG_NOSIGNAL so it returns EPIPE instead; the launch configs also tell gdb not
to stop on it.

A hang is almost always a blocking syscall. accept() and recv() ignore
stop_token - a std::stop_token cannot interrupt a syscall. That is why main
calls shutdownConnection(fd) before the jthread destructor joins: shutdown()
makes a blocked recv() return 0, while close() does NOT wake it (and frees the
fd number for reuse, which is worse). On a hang:

    (gdb) thread apply all bt

Breakpoints worth having:

    (gdb) break connectToClient
    (gdb) break recvFrame
    (gdb) print/x *(unsigned char*)header@8     # the 8 header bytes
